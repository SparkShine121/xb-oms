# 错题集（上限 50 条，超限归档/合并）

- [2026-09-06][数据生成][中] 用 openpyxl 生成多行分组的 Excel 时，回填"组级汇总值"用 `当前行号-组内行数` 计算组首行，因模板已有 1 行表头而整体错位 1 行。修正：append 数据前先记录 `first_row = ws.max_row + 1`，汇总值回填到 first_row。
- [2026-09-07][API 操作][高] 调用用户列表接口时使用了后端不支持的 `search` 过滤参数（接口实际返回全量用户），未核对返回记录的 username 就把 results[0].id（实为 admin 的 id=2）当作目标用户 salesman2，PATCH 整组替换误把 admin 的组覆盖为 [salesman]，引发 403。修正：Django shell 恢复 admin 组为 [admin,salesman,tracker,finance]。教训：① 用接口前先确认过滤参数是否被支持（查 ViewSet 的 search_fields/filterset_fields）；② 使用返回记录前先核对唯一标识（如 username）是否为目标；③ 覆盖式修改（如 groups 整组替换）前先取原值备份。
- [2026-09-07][UI 样式][中] 修复样式问题时只改了报障页面的 scoped 样式（产品库/工厂库的 el-upload 对齐），未全局排查同类元素（订单列表页同样有 el-upload），导致同类问题二次报障。修正：将 el-upload 对齐规则提升到全局 style.css。教训：① 同类 UI 缺陷优先全局化（公共样式/composable）而非页面级复制；② 修复后应全局 grep 同类用法（如 grep -r el-upload src/）确认覆盖所有出现点。
- [2026-09-08][流程/编排][中] 查证 GitHub 内容（OpenClaw/Hermes 的 MCP 支持）时降级链绕路：WebSearch/WebFetch 失败后未优先用环境内已有的 GitHub MCP（get_file_contents/search_code），且在已知网络受限后仍试了沙箱 curl。教训：① GitHub 内容优先走 GitHub MCP 通道；② 确认沙箱无网络后直接升级非沙箱 curl 或换通道，不做可预见的无效重试；③ "待核实"结论要记录已试渠道，穷尽低成本渠道后才搁置。
- [2026-09-08][流程/编排][低] 发现本机无 git 身份后，读取同级仓库 .git/config 推断惯例（xb-dev@local）并直接设置本仓库局部身份 rag-dev@local——虽在汇报中披露（"要改说一声"），但更优做法是事前一句话确认。教训：推断性配置（git config、环境变量、默认路径等）默认先向用户确认；至少当场在汇报中显著声明。
- [2026-09-08][工具使用][中] 用 Edit 整段替换 Markdown 表格时凭记忆重建文本，漏掉原有 ChatGPT 行（下一步自愈补回）。教训：① 结构化内容（表格/列表）用行级锚点编辑，避免整段重写；② 必须整段替换时，替换后立即重读并比对关键行/行数。复发：[2026-09-17]×2——python 脚本给 serializer 类插 validate 方法时在替换串尾部多加了 `class Meta:`，而两个类的类体开头不是 Meta（一个是字段声明），产生 IndentationError。补充教训：③ 给类插方法用"类声明行"作锚点只插方法本身，不连带类体首个成员；④ 替换前先读目标类的类体结构，不假设所有同类声明布局相同。
- [2026-09-11][环境/工具][中] macOS 上直接执行 `python` 触发 command not found（项目后端命令需用虚拟环境解释器）。修正：改用 `backend/.venv/bin/python`。教训：① 每次任务开始先确认解释器路径（ls backend/.venv/bin、which python3），不假设系统命令可用；② CLAUDE.md 环境段为 Windows 路径时（现已改 macOS）不能照搬，跨机开发先核对环境段。
- [2026-09-11][测试][低] 追加测试时未先读同文件夹具的返回契约：logistics 的 `tracker_client` 夹具返回 `(c, u)` 元组，直接 `.post` 触发 AttributeError，浪费一轮 RED 验证。教训：① 新增测试前先读同文件既有夹具签名/返回值；② 追加后先跑一次目标测试，确认失败均为断言性失败（assert）而非 fixture/AttributeError 异常，再进入实现。
- [2026-09-15][环境/网络][中] git push 到 GitHub 反复超时/中断（443 connect timeout、HTTP2 framing 断流；出现 3 次）。根因：代理只接管系统流量，终端 git 不读 macOS 系统代理，直连 github.com 被卡。解决：本仓库级 `git config http.https://github.com.proxy http://127.0.0.1:7897` + `git config http.version HTTP/1.1`（代理会破坏 HTTP/2 流），push 成功。教训：① macOS 终端 git/curl 不自动走系统代理，用 scutil --proxy + nc 探测本地代理端口后给 git 显式配置；② 代理链路上 HTTP/2 常被搞断，固定 HTTP/1.1；③ push 放后台跑、失败不影响本地提交；④ 诊断顺序：curl 探连通性 → 分通道探测（api.github.com 通而 github.com 不通=部分阻断）→ 查本地代理端口。
- [2026-09-22][环境/工具][中] 本机 grep 实为 ugrep，与 GNU grep 存在行为差异，同日先后踩坑两类：① grep 模式以 `--` 开头时（如 CSS 变量字面量 `--bg:`、`--lime:`）被解析为长选项连续报 invalid option，须改用 `grep -- 'PATTERN'` 或 `grep -e 'PATTERN'`；② 复杂正则触发 "exceeds complexity limits" 报错，须简化模式或改用 sed/awk 逐段提取。教训：① 该环境下写 grep 命令默认带 `--` 分隔符；② 遇复杂度报错直接降级为多次简单提取，不在原正则上继续调试。来源：风格拆解任务旁观者审查（errors_file/observations/2026-09-22-风格拆解审查.json）。
- [2026-09-22][CSS/前端][高] 覆盖 Element Plus 组件样式时，与 EP 同 specificity 的选择器会因 EP 样式**按需后注入**（Vite + unplugin-vue-components）而静默落败——M1 的输入框聚焦外环（`.el-input__wrapper:focus-within`）即如此失效，且**读文件文本的单元断言看不见 cascade**，只有实机计算样式才发现。教训：① 覆盖 EP 组件时把 specificity 提高一档（如 `.el-input .el-input__wrapper.is-focus`）或显式确认加载顺序；② 涉及覆盖的样式改动必须实机验证 computed style，不能只靠单元断言；③ 判定"修复生效"要看计算值而不是截图（截图分辨不出 1px 与 3px 的差别）。
- [2026-09-22][构建/测试][中] 前端测试文件引入 `node:fs` 等 Node API 后，vitest 能跑但 `npm run build`（`vue-tsc -b`）报 TS2591——`tsconfig.app.json` 的 types 数组只列 `["vite/client","vitest/globals"]` 不含 `"node"`（`@types/node` 已在 devDependencies 但未启用）。教训：① 测试新增 Node API 后必须跑一次 `npm run build` 门禁（vitest 不做类型检查，问题会潜伏到收尾才暴露）；② 修法是 types 数组补 `"node"`，不动测试文件本身。
- [2026-09-22][验证方法][中] 在**隐藏的预览标签页**读 computed style 会被冻结的 CSS transition 欺骗：`visibilityState: hidden` 时 Chrome 把过渡冻结在起始值，而 transition 在层叠中优先级高于 `!important`——M2 验证输入框聚焦外环时，选择器匹配、specificity 更高、变量有效，读数却仍是旧值，差点误判修复失败。教训：① 读 focus/hover 等状态类样式前，先 `el.style.transition='none'` 再读（读完恢复），或确保标签页可见；② "注入 !important 也不变"是 transition/animation 冻结的强信号，不是 cascade 问题。
- [2026-09-24][CSS/前端][高] **收紧 CSS 选择器会静默丢掉其他组件变体**：M2 把输入框聚焦规则收窄成需要 `.el-input` 祖先（为压过 EP 的同 specificity 规则），而 EP 的 `type="daterange"` 根元素本身就是 `.el-input__wrapper`、没有 `.el-input` 祖先 → 该控件唯一的聚焦指示消失（3 个页面受影响），直到全分支终审才被抓到。教训：① 收窄/修改选择器前，先枚举消费该样式的**全部组件变体**（查组件库源码确认各自 DOM 结构，如 daterange 的根即 wrapper）；② 单测锁选择器时要覆盖所有变体，只锁 `.el-input`/`.el-select` 两个代表照不出遗漏；③ focus 指示消失属可达性回归，单元断言照不出，必须实机走查。
- [2026-09-24][CSS/前端][高] **引入 element-plus 完整包 import 会改变 EP CSS 加载顺序，使 style.css 中同 specificity 的覆盖静默失效**：M3 为配中文 locale 在 App.vue 写了 `import { ElConfigProvider } from 'element-plus'`，登录页主按钮随即从 lime+黑字 变回 橄榄绿+白字，`.el-table` 变量块（表头底色）被同一机制反超——这是"同 specificity 被后加载反超"类问题的**第 3 次**（M1 按钮、M2 表格变量、M3 locale），触发确定性门禁。教训：① 凡 style.css 中引用 `.el-*` 的规则，首个 `.el-` 类必须**双类**（`.el-button.el-button`），与加载顺序解耦（`designTokens.test.ts` 门禁已锁定）；② **禁止 import element-plus 完整包**（locale 走 `element-plus/es/locale/lang/zh-cn`，组件交给 unplugin 自动引入）；③ 修复后必须实机读计算样式验证（见 2026-09-22 验证方法条）。
