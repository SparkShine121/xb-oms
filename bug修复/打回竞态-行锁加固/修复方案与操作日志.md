  - Q2:a 测试策略：并发窗口在 SQLite 测试基建下无法真实复现（select_for_update 仅 MySQL 生效是既有口径；多线程共享测试连接不可行）——本批为**不可测的加固**，不写假测试，以既有全量回归（锁不破坏既有语义）+ 旁观者审查验证

## 竞态时序（修复对象）

1. **编辑内容逃逸审批**：未批准单 O + pending AR-1；admin approve（置 True）与非 admin 编辑（快照读到 False → 不触发打回）并发 → O=True 且编辑内容生效未挂审，024 语义被绕过
2. **快照旧值覆盖**（推演新发现，比 1 更糟）：serializer.save() 走 Django 全字段 UPDATE（无 update_fields 时），以 get_object 快照写回——并发 approve 刚写的 `is_approved=True` 会被编辑请求的快照 False 覆盖 → 订单卡"未批准"且无 pending AR，无人审批
3. **AR 残留**：打回置 False+建 AR-2 与 approve 置 True 交错 → pending AR 残留（重复批准无害，cleanup-orphans 可清，审查已判可接受；锁把窗口缩到最小）

## 实现（两侧写窗口互斥，锁序一致无死锁）

1. **三处打回（Order/FP/FPRecord perform_update）**：`transaction.atomic` 内先 `select_for_update` 锁目标行**重读**，`serializer.instance = locked`（save 作用于锁内最新实例——修复快照覆盖），后 save；打回判断以锁内 DB 最新 `is_approved` 为准。FPRecord 保持 Record→fp 锁序；Order 顺带补包 atomic（原无事务）
2. **approve（system_mgmt）**：事务内 AR 行锁重读 status（非 pending → 400，双 approve 串行化）→ target 行锁重读再置 True（与打回写窗口互斥）→ FPRecord 场景保持既有 fp 锁重算（锁序 target→fp 与编辑侧一致）
3. 锁序总表：approve = AR→target→(Record 场景) fp；编辑 = target→(Record 场景) fp。AR 锁仅 approve 持，无交叉 → 无死锁

## 验证口径

- 既有后端全量（316）零改动通过 = 锁不破坏任何既有语义（approve 重复 400、打回语义、超付校验、自愈 cancelled 均为既有行为锁内保持）
- 锁行为本身靠实现 + 审查（MySQL 生产生效；SQLite 测试跑不到锁，靠事务原子性兜底——既有口径）
- 时序 1/2 修复逻辑经推演核验（approve 先→编辑后锁重读 True→打回 ✓；编辑先→approve 后锁串行 ✓）

## 边界

- 极端"打回与 approve 同一瞬间"的双 AR 交错仍可能残留 pending AR（无害，cleanup-orphans 兜底）——锁缩小窗口但不改变双写语义
- 锁仅 MySQL 生产真实生效（SQLite dev 环境依赖事务原子性+单进程低并发，风险口径与 BUG-SIM-008-010 并发批一致）
