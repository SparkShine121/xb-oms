## 门禁语义（全系统权威定义）

**未批准 = 不产生业务效果**：

| 模型 | 未批准时的效果 |
|---|---|
| Order | 不可推进/驳回；不可生成结算；明细不可新建结算 |
| FactoryPayment | 不可登记付款；不进工厂汇总；不进对账单 |
| FactoryPaymentRecord | 不计入结算单已付（approve 时重算） |
| Logistics | 无下游聚合，"视为未发出"天然成立（归档注明） |

冻结保留：订单编辑/驳回后修改重提（审批闭环）。approve 三步包 atomic（⑯ 顺带）。

## 实现

1. `tracking/services.py::_move`：advance/reject 检查 `fresh.is_approved` → 400"该订单待审批通过后可流转"
2. `generate_by_order`：订单未批准 → 400（门禁拒绝，区别于取消单的 skipped 语义）
3. `FactoryPaymentSerializer.validate`（create）：明细属未批准订单 → 400
4. `FactoryPaymentRecordSerializer.validate`（create）：挂未批准结算 → 400
5. `Record.save/delete` 聚合：只计 `is_approved=True` 的记录；`approve` action 对 FactoryPaymentRecord 类型触发父单重算
6. 工厂汇总/对账单：排除未批准结算单
7. **024**：`OrderViewSet.perform_update`——非 admin 编辑已批准订单 → is_approved=False + 重新挂 order_change 审批（与 resubmit_on_update 的 pending 判重自然协同）
8. 前端 OrderList：is_approved=false 显示"待审批"tag
9. 存量核查脚本式查询并汇报

## 审批门禁对既有流程的行为变化（重要）

- finance 登记付款记录 → 挂审批（is_approved=False）→ **不计入已付/流水**，admin 批准后重算计入——付款从此有真实审批约束力
- 未批准结算单不进工厂汇总/对账单——admin 批准后生效
- **待审记录占用超付额度**（_check_overpay 统计全部记录），防"两次待审都放行后超付"
- 非 admin 编辑已批准订单 → 打回未批准+重挂审（含备注级修改，Q4:a 零绕过）
