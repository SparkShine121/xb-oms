# BUG-SIM-001 修复方案 · bulk-delete 绕过删除权限

- 日期：2026-09-11 ｜ 基线：`d5a4c3a`（dev）｜ 分支：`feature/bug-sim-001-bulk-delete`（自 dev 拉出，完成后合并回 dev）
- 状态：方案已确认（Q1:A Q2:a Q3:ii Q4:ii），待实施

## 1. 问题描述

业务员单条 DELETE 返回 403 的同一资源，可通过 `POST /api/<资源>/bulk-delete/` 批量删除成功；范围外 id 被静默跳过不报错。

## 2. 根因（代码级）

1. `backend/common/views.py:34-45`：`bulk_delete` 挂在 `BaseModelViewSet` 上，**所有 ViewSet 自动继承该端点**。它只逐对象调用 `has_object_permission` 兜底，从不按 `destroy` 语义走操作级权限——各权限类里写死的"删除禁令"全部以 `view.action == 'destroy'` 为条件，action 实为 `bulk_delete` 时全部失效
2. 各 app 权限类 `has_object_permission` 末尾兜底 `return True`（如 `orders/permissions.py:28`），或根本没有对象级方法（factory_payment/logistics/finance）

### 暴露面实测

| 端点 | 权限类 | 修复前非 admin 批量删 |
|---|---|---|
| orders | OrderPermission | salesman/tracker 删自己数据范围、finance 删全部 ❌ |
| payments ×2（factory_payment） | FactoryPaymentPermission | 全部角色可删 ❌ |
| shipments（logistics） | LogisticsPermission | 全部角色可删 ❌ |
| payments-in（finance） | FinancePermission | 全部角色可删 ❌（前端无入口，端点裸露） |
| basic_info ×5 | AdminWriteOthersReadOnly | 已安全（POST 非 admin 403）✔ |
| users / exchange-rate / system_mgmt | RolePermission / AdminOnlyPermission | 已安全 ✔ |

### 同源缺陷（本次一并修）

- 删除循环无事务：中途异常留下半删状态 → `transaction.atomic` 包裹
- 范围外 id 静默跳过（= BUG-SIM-025）→ 响应带 `not_found` 清单

## 4. 修复设计

### 4.1 后端 `common/views.py`（唯一代码改动点）

```python
@action(detail=False, methods=['post'], url_path='bulk-delete')
def bulk_delete(self, request, *args, **kwargs):
    ids = request.data.get('ids') or []
    if not isinstance(ids, list) or not ids:
        return error_response(1001, '未指定要删除的记录', status=400)
    original = self.action
    self.action = 'destroy'          # 按"单条删除"的规则校验
    try:
        try:
            self.check_permissions(request)          # 操作级（等价单条 DELETE）
        except PermissionDenied:
            return error_response(1003, '没有删除权限', status=403)
        found = {obj.pk: obj for obj in self.get_queryset().filter(pk__in=ids)}
        forbidden, not_found, deleted = [], [], 0
        with transaction.atomic():                    # 消除半删状态
            for oid in ids:
                obj = found.get(oid) or found.get(int(oid)) if str(oid).lstrip('-').isdigit() else found.get(oid)
                if obj is None:
                    not_found.append(oid); continue
                try:
                    self.check_object_permissions(request, obj)   # 对象级（等价单条 DELETE）
                except PermissionDenied:
                    forbidden.append(oid); continue
                obj.delete(); deleted += 1
    finally:
        self.action = original
    if deleted == 0 and forbidden and not not_found:
        return error_response(1003, '没有删除权限', status=403)
    return success_response(
        {'deleted': deleted, 'forbidden': forbidden, 'not_found': not_found},
        message='已删除')
```

要点：
- `self.action = 'destroy'` 期间完成 `check_permissions` + `get_queryset` + 逐对象 `check_object_permissions`，结束后恢复原 action；各 ViewSet 的 `get_queryset` 不按 action 分支（已核实 orders/basic_info 等），数据范围不变
- id 统一按 pk 匹配（兼容字符串数字），重复 id 天然幂等
- 403 语义：仅当"一条都没删、且每一条都是权限拒绝"时整体 403（与单条删除语义对齐）；混合 forbidden/not_found 时返回 200+清单
- 响应新增 `forbidden`/`not_found` 字段，`deleted` 由数量改为仍为数量（向后兼容：前端旧逻辑不读响应体）

### 4.2 前端 `src/composables/useBulkDelete.ts`

`handleBatchDelete` 读取响应 `data`：
- 无 forbidden 且无 not_found → `已删除 N 条`（现状）
- 有跳过 → warning：`已删除 X 条，Y 条无权限，Z 条不存在`
- 后端 403（全部禁删）→ axios 拦截器已有全局错误 toast，composable 不额外处理（`await` 抛出后跳过成功提示，现有行为保持）
