## 实现

1. **021 删用户（transfer_to 模式）**：`UserViewSet.perform_destroy` 重写——
   - 校验：防自删（400"不能删除当前登录账号"）；末位 admin 保护（唯一 admin → 400）
   - 名下有客户/订单（Customer.salesman / Order.salesman / Order.tracker 引用）→ **必须传 `transfer_to`**（存在且非本人，400 带数据量提示）；无业务数据 → 可不传
   - 转移规则（**待确认的关键语义**，见下）+ `transaction.atomic` 内转移 → 删除
2. **028 停用**：`UserManageSerializer` 暴露 `is_active`（create/update）；停用置 False 时该用户全部 refresh token blacklist（019 基建）；前端用户列表加"停用/启用"开关（确认弹窗）；停用即时生效——simplejwt `get_user` 对 is_active=False 的 access 下一次请求即 401（快于 30min 自然死）
3. **023 路由守卫**：4 条 system 路由加 `meta: { roles: ['admin'] }`（menuConfig 已有 adminOnly 数据源呼应）；守卫检查 roles 无交集 → ElMessage"无权访问" + 跳首页；后端 AdminOnlyPermission 仍是防线
4. 前端 UserManage：删除弹窗按需选承接人（下拉列其他用户）；列表显示 is_active 状态 tag

## 转移规则（Q1:b 的两个子语义，确认后生效）

| 数据 | 转移动作 |
|---|---|
| Customer.salesman = 被删用户 | → 承接人 |
| Order.salesman = 被删用户 | → 承接人 |
| Order.tracker = 被删用户 | 承接人含 **tracker 角色** → 转给承接人；否则 → **置空**（待重新派单，符合 014"tracker 必须 tracker 角色"） |

（承接人一个参数；不拆双承接人——内部系统够用且交互简单）
